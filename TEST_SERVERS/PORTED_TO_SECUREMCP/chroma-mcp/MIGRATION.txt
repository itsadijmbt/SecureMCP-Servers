chroma-mcp: FastMCP -> SecureMCP migration
==========================================

WHAT WE DID
-----------

src/chroma_mcp/server.py -- two active-code lines changed:

  1. Import swap:
       was: from mcp.server.fastmcp import FastMCP
       new: from macaw_adapters.mcp import SecureMCP

     Original preserved as a `# was: ...` comment immediately above the
     new import line (skills file preamble rule).

  2. Server instantiation swap:
       was: mcp = FastMCP("chroma-mcp")
       new: mcp = SecureMCP("chroma-mcp")

     The single module-global server object is now SecureMCP. By the
     time mcp.run() is called in main(), every @mcp.tool(...) decoration
     in the file has already populated self._tools at import time, the
     same way it did under FastMCP. SecureMCP prepends `securemcp-` to
     the name when registering the app-agent on the MACAW mesh
     (`app_name=f"securemcp-{self.name}"` at mcp.py:707), so the
     user-visible agent_id becomes:
         local:<user>/app:securemcp-chroma-mcp:<hash>
     Downstream filtering uses the substring `chroma-mcp` to locate
     the agent.

     Original preserved as `# was: mcp = FastMCP("chroma-mcp")`
     immediately above the new line. The pre-existing upstream comment
     `# Initialize FastMCP server` was rephrased to
     `# Initialize the MCP server (was FastMCP under the slim SDK).`
     to avoid an actively-misleading description.

That is the entire framework-level work.

src/chroma_mcp/server.py -- everything else is UNCHANGED from upstream:

  - create_parser() retains all seven CLI flags including --client-type,
    --host, --port, --tenant, --database, --api-key, --ssl,
    --data-dir, --custom-auth-credentials, --dotenv-path. These are
    Chroma-side database backend configuration, not MCP transport, and
    therefore stay per skills file Step 1d ("unless it is embedded in
    business logic").

  - get_chroma_client(args) retains its full four-branch dispatch on
    args.client_type: 'http' -> chromadb.HttpClient(host=..., port=...,
    ssl=..., settings=...); 'cloud' -> chromadb.HttpClient(
    host="api.trychroma.com", ssl=True, tenant=..., database=...,
    headers={'x-chroma-token': api_key}); 'persistent' ->
    chromadb.PersistentClient(path=args.data_dir); ephemeral default ->
    chromadb.EphemeralClient(). The module global `_chroma_client`
    pattern is preserved.

    NOTE: an earlier draft of this port commented out the `elif
    args.client_type == 'persistent':` dispatch line while leaving its
    body inline. Python re-attached the dangling 12-space `if not
    args.data_dir:` and `_chroma_client = PersistentClient(...)` lines
    inside the `if args is None:` block, and the `else: # ephemeral`
    line attached to that same `if args is None:` -- with the result
    that `main() -> get_chroma_client(args)` (args always non-None)
    unconditionally landed on EphemeralClient regardless of
    --data-dir. That was a silent data-loss bug. The fix in this port
    is to keep the full four-branch dispatch intact and to leave the
    framework swap as the only modification.

  - main() retains its dotenv-reload block and its per-client-type
    validation (parser.error on missing host/tenant/database/api_key).
    The final call is mcp.run() with no arguments; SecureMCP defaults
    to transport="stdio" at mcp.py:596.

  - All tool decorations (@mcp.tool(description=...)) and tool bodies
    are unchanged. Verified by grep across server.py for `await ctx.`,
    `timeout=`, `annotations=`, `tags=`, `mime_type=`, `output_schema=`,
    `structured_content=`, `Annotated[`, `Field(`, `pydantic` -- the
    Chroma tools use plain Python type hints (str, int | None,
    Dict | None, List[str], etc.) with no FastMCP-specific kwargs and
    no pydantic Field metadata at tool boundaries.

  - The module global `_chroma_client` is process-scope, not
    `_session_objects`. Chroma has no per-user session model -- one
    client per process is correct (skills file Step 4: "Module
    globals -- for process-scope, no per-user identity"). Hard Rule 11
    (default to process-scope) satisfied.

pyproject.toml -- fastmcp / mcp[fastmcp] dependency removed; the new
dependency is the macaw_adapters package (installed from the
workspace's secureAI/ via `pip install "./secureAI[all]"` per the
workspace README).


WHY
---

The chroma port is structurally compatible with SecureMCP's narrower
surface from the start:

  - No FastMCP middleware (no add_middleware calls, no Middleware
    subclasses, no per-tool timeout enforcement, no structured_content
    declarations, no MIME-typed Resources).
  - No FastMCP lifespan= kwarg (the chroma client is managed lazily
    via the module global `_chroma_client` and `get_chroma_client()`,
    which matches Step 4 "Lazy async setup -> PORT" guidance).
  - No FastMCP-internal monkey-patches.
  - No transport branching in the entry point (mcp.run() is called
    directly).
  - Tool signatures use plain Python type hints from the start -- no
    pydantic.Field, no Annotated[Field(...)] metadata, no
    BaseModel-as-input. SecureMCP's _extract_parameters (mcp.py:822-854)
    reads inspect.signature directly and maps str/int/float/bool/dict/
    list through the 6-entry type_map. Optional/union types
    (`int | None`, `Dict | None`) fall through to "string" -- documented
    in KNOWN GAPS below.
  - No subclassing of FastMCP. The module-global instantiation pattern
    works identically under SecureMCP.

The two-line server.py change is the entire framework-level work.


BROKEN ON PURPOSE
-----------------

None.

The original had no per-tool timeout, no structured_content fixup, no
MIME-typed Resources, no FastMCP-specific tool annotations or icons,
and no middleware. There is nothing the port silently dropped that the
original was using. All four Chroma client backends (http, cloud,
persistent, ephemeral) remain reachable.

Behaviour-diff (skills file Step 9c):

  Chroma-layer behaviour is byte-for-byte unchanged -- tool signatures,
  return values, error messages, client backend dispatch. The envelope
  around each return is SecureMCP's `{"result": value}` wrap for
  non-dict returns (mcp.py:810-812); dict returns are passed through.
  MACAW callers either unwrap explicitly with
  `result.get("result", result)` or consume the wrapped dict directly
  -- this is the MACAW convention, not a chroma-specific delta.


KNOWN GAPS
----------

1. Per-parameter descriptions are not advertised to the MACAW caller.
   SecureMCP's _extract_parameters (mcp.py:822-854) emits only
   {name, type, required, default} per parameter -- no description
   field. The tool-level description (passed to @mcp.tool(description=
   ...)) IS advertised correctly. Per-parameter docstring text from
   Args: blocks survives in the source code but does not reach the
   wire.

2. `int | None`, `Dict | None`, `Optional[X]`, and other union or
   generic types in tool signatures fall through to "string" in the
   advertised schema. The 6-entry type_map at mcp.py:837-844 keys on
   bare class objects (str, int, float, bool, dict, list). The tool
   bodies still receive the correctly-typed value because Python does
   no runtime type enforcement and the MACAW transport passes raw
   JSON values; only the schema advertisement is lossy.

3. The `import ssl` (server.py:9) and `from dotenv import load_dotenv`
   (server.py:6) imports are active because they are used by the
   http/cloud branches of get_chroma_client and by the dotenv reload
   in main(), respectively. No dead imports.

4. README.md retains upstream Chroma branding. Per skills file
   Step 11 ("Unchanged in a correct port: business-logic modules,
   transport runners that wrap mcp.run()..."), README rewrites are
   not part of the port discipline. This MIGRATION.txt is the port's
   documentation contract.
