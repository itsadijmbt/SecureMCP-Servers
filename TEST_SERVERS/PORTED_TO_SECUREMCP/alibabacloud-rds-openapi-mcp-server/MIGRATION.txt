MIGRATION: alibabacloud-rds-openapi-mcp-server, FastMCP -> SecureMCP
Upstream base: aliyun/alibabacloud-rds-openapi-mcp-server @ aaadba9 (2026-03-20)

WHAT
- core/mcp.py: RdsMCP(FastMCP) became a class that holds a SecureMCP. The
  grouping and delayed registration logic is upstream's. activate() passes only
  name / description / prompts to SecureMCP.tool() (it accepts nothing else).
- server.py: the HTTP branch of main(), VerifyHeaderMiddleware and the /health
  route are commented out. mcp.run() serves stdio. Every tool is upstream's.
- utils.py: identical to upstream.
- pyproject.toml: requires-python lowered from 3.12 to 3.11.

CORRECTED IN THIS REVISION (2026-10-12)
- The "metadata as request headers" wrapper is removed. The first port added a
  ctx parameter and a "with metadata_as_request_headers(ctx):" block to 36
  tools, and a helper in utils.py that read the private ctx._metadata.
  What was checked before removing it:
    1. MACAW puts nothing in ctx.metadata. A live call showed {"roots": []}.
    2. The only way to fill it is for the caller to send a tool argument named
       "_metadata". So cloud keys would travel as an ordinary tool argument.
       A normal MCP client never sends it: it is not in the published schema.
    3. Upstream fills current_request_headers only on its HTTP transports.
       On stdio it stays {} and get_aksk() reads the ALIBABA_CLOUD_* variables.
  The 36 tools now have upstream's exact text again (checked tool by tool) and
  the port behaves like upstream on stdio: credentials come from the
  environment of the server.
- 6 Field(...) defaults flattened (show_largest_table and
  show_largest_table_fragment: region_id, dbinstance_id, topK). A left-out topK
  used to reach the SQL text as a FieldInfo object. Descriptions are in the
  docstring.
- 42 tool parameters given a plain type: 13 in server.py, 18 in
  tools/rds_custom_action.py, 11 in tools/rds_custom_read.py. Old type kept in
  "# was:".
- client-test-macaw.py: the test that sent fake keys in "_metadata" is removed.

WHY
SecureMCP publishes six parameter types: str, int, float, bool, dict, list.
Anything else is published as "string", and it does not understand Field.

BROKEN ON PURPOSE
- HTTP transports, the API_KEY bearer check and the /health route.
- Per-request credentials. Upstream's HTTP mode let each request bring its own
  ak / sk / sts and rds_user / rds_passwd in HTTP headers. There are no HTTP
  headers here. One server process uses one set of keys.
- Tool annotations (READ_ONLY_TOOL) are not published.

KNOWN GAPS
- The server name "Alibaba Cloud RDS OPENAPI" has spaces. On 0.9.10.1 a served
  server with spaces in its name answered calls normally, and the policy id
  uses the same name, so it is left as upstream has it.
- RdsMCP holds a SecureMCP instead of inheriting from it. It works and was left.

VERIFICATION (2026-10-12, macaw-adapters 0.9.10.1, macaw-client 0.9.10.1)
- 36 tools compared with upstream: identical.
- Served through MACAW with run("stdio") and called as a normal MCP client,
  with the Alibaba SDK installed and no cloud keys set. 36 tools published,
  list / dict / int parameters published as array / object / integer.
  get_current_time worked. describe_db_instances returned the SDK's
  InvalidCredentials error (environment path). The same call with a
  "_metadata" argument is refused ("unexpected keyword argument").
- restart_db_instance is denied in Policy/server_policy_v0.1.json but was not
  blocked in this run, so that policy was not applied in the test workspace.
- Not run against a real Alibaba Cloud account.
